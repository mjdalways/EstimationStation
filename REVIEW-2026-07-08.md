# EstimationStation Code Review — 2026-07-08

Fix-ready findings from a full-codebase review. Each item has file:line anchors and fix guidance. Line numbers reference the working tree as of 2026-07-08 (includes the uncommitted Feature8 P1–P5 changes). Severity: 🔴 fix now · 🟡 should fix · 🔵 nice-to-have / decision needed.

## A. Fake-avatar double check (2D/3D) — verdict

The tab-close/reopen doppelganger is **fixed** (server same-name reconciliation in `JoinRoom`, client `_seedRoamersFromParticipants` self-skip, `applyClaim` same-cid/same-name eviction, `_rebuildSeating` dual cid/name seated guards, `syncParticipants` roamer cleanup). **One real ghost-avatar path remains, plus two small hardening items:**

### 🔴 A1. Kick / leave-timeout / idle removal never frees the server-side chair claim
- `Services/RoomService.cs:128` `RemoveParticipant` removes the participant and transfers host but does NOT touch `room.ChairClaims`. `Hubs/PokerHub.cs:963` `RemoveAndBroadcastAsync` never broadcasts `ChairReleased`. Contrast with `LeaveRoom` (PokerHub.cs:197–201) which frees chairs and broadcasts.
- Consequence: after a host kick, "are you there?" timeout, or the 2-hour idle sweep, the removed user's claim stays in `room.ChairClaims` (and is persisted). Present clients look fine (their `ParticipantLeft` handler calls `RS3D.releaseByConnection`), but **every later joiner or reloader receives the stale claim in RoomState and `_rebuildSeating` (wwwroot/js/room-scene-3d.js:4258) draws a gray "ghost" seated robot** with no matching participant — in both 2D (top view) and 3D. It stays until someone manually double-clicks that chair.
- Fix (server, primary): in `RoomService.RemoveParticipant`, inside the existing `lock(room)`, also remove all `ChairClaims` entries whose `ConnectionId == connectionId`, return the freed indexes in `RemovalResult`, and have `PokerHub.RemoveAndBroadcastAsync` broadcast `ChairReleased(idx)` for each.
- Fix (client, belt & braces): in `_rebuildSeating` at the `if (!p)` ghost branch (room-scene-3d.js:4258), skip drawing the ghost when `_claimIsStale(claim)` (helper already exists at :3604) — render the chair as unclaimed instead.

### 🟡 A2. Transient duplicate on rejoin (cosmetic)
`JoinRoom` broadcasts `ParticipantJoined` for the new cid (Hubs/PokerHub.cs:153) BEFORE `ParticipantLeft` for the reconciled stale cid (:170). Other clients briefly hold both entries (same name, two cids) and can paint two badges / two standing robots for one message beat. Fix: send the stale `ParticipantLeft`s (and chair re-keys) before `ParticipantJoined`, or dedupe in the client handler (A3).

### 🟡 A3. `ParticipantJoined` client handler has no dedupe
wwwroot/js/room.js:248 pushes without checking for an existing entry. Cheap hardening: `roomState.participants = roomState.participants.filter(x => x.connectionId !== p.connectionId && x.name !== p.name); roomState.participants.push(p);` (at minimum filter by connectionId).

### 🟡 A4. Same-name takeover zombifies a live duplicate-named user
`JoinRoom` reconciliation (PokerHub.cs:100–138) assumes same display name = same person. If two *different* people use the same name, the second join silently removes the first, steals their avatar/chair/host, and `RemoveConnection(oldCid)` unmaps the live connection — the first user's tab stays open but every hub call silently no-ops with no notification. Fix: send `RemovedFromRoom("superseded")` to each stale connectionId (client already handles `RemovedFromRoom`, room.js:690/3113) so the older tab shows a message and navigates home.

## B. Server bugs (Hubs/Services)

### 🔴 B1. Culture-dependent vote parsing
`Hubs/PokerHub.cs` `CalculateStats` (~:1530) and `FindShameParticipantId` (~:1422) use `double.TryParse(p.Vote.Replace("½","0.5"))` with the server's current culture. On comma-decimal cultures (de-DE etc.) "0.5"/"13" style parses fail or misparse, so votes silently vanish from stats/shame. Fix: `NumberStyles.Float, CultureInfo.InvariantCulture` (as `WriteJiraEstimate` already does at :1367).

### 🔴 B2. `BuildRoomState` returns lazy LINQ over mutable collections
PokerHub.cs:1484/1497/1511 — the anonymous state object holds *deferred* `Select` enumerables over `room.Participants`/`Stories`/`ChairClaims`. SignalR serializes them after the method returns, outside any lock; a concurrent join/leave throws "Collection was modified" and the joiner's `RoomState` send fails (they see an empty room). Fix: materialize with `.ToList()` inside `lock(room)` (build the whole object under the lock).

### 🟡 B3. Unlocked `Participants` reads race with locked mutations
`AvatarMove` (:386), `AvatarStop` (:400), `TransferHost` (:878), `RemoveParticipant` guard (:892), `SendPrivateMessage` (:1073–1075), `SendPrivateReaction` (:1091), `SendSoundToParticipant` (:1103), `TriggerCustomSound` (:1356), and `ParticipantSweepService.SweepAsync` (Services/ParticipantSweepService.cs:51,54) enumerate `room.Participants` (a `List<>`) without `lock(room)` while JoinRoom/LeaveRoom mutate under lock. Can throw or produce torn reads. Fix: wrap those reads in `lock(room)` (pattern used everywhere else). `AvatarMove`/`AvatarStop` also *mutate* participant fields unlocked.

### 🟡 B4. `SetCurrentStory` half-resets the round
PokerHub.cs:767–787 clears `Vote` + `VotesRevealed` only; `ResetVotes` (:590) also clears `IsGhost`, `Confidence`, `ShameParticipantId`, and `Vibes`. Switching story leaves stale confidence/ghost/vibes on the server while clients render as reset (they receive `VotesReset`), so the next reveal shows stale confidence values. Fix: share one reset helper between both methods.

### 🟡 B5. `WhiteboardDraw` never marks the room dirty
PokerHub.cs:310–326 appends the stroke but doesn't call `_roomService.SaveRoom(room)` (WhiteboardClear does). Strokes only persist when something else dirties the room — a restart shortly after drawing loses the board. Fix: add `_roomService.SaveRoom(room);` after the lock.

### 🟡 B6. `ExecuteSettingChange("estimateSet")` can throw
PokerHub.cs:1056 — `Deserialize<Dictionary<string,string>>(valueJson)?["set"]` throws `KeyNotFoundException` on a crafted/malformed request. Use `TryGetValue`.

### 🟡 B7. Vote/custom-estimate values unvalidated
- `CastVote(string vote)` (:519) stores any string up to the 1 MB hub cap per participant and persists it. Validate against the room's current estimate set or cap length (~16 chars).
- `SetEstimateSet` (:1112) has no length/count cap on `customValues` (every other mutator caps input). Cap (e.g. 500 chars / 50 values).

### 🟡 B8. In-memory rooms never evicted; deleted rooms can resurrect
`RoomService._rooms` grows forever. `RoomCleanupService` deletes the file + media of a 30-day-stale room but not the in-memory entry, so it stays in `ActiveRooms` and any later `FlushDirty` re-creates the file. Fix: add an eviction API on RoomService and call it from RoomCleanupService (guard with `lock(room)` + participant-count check).

### 🔵 B9. Minor server items
- `RoomService.RemoveConnection` (:164–170) does a synchronous `_repo.SaveRoom` on the hub thread — inconsistent with the coalesced dirty-flag design; just mark dirty.
- PIN only guards non-empty rooms: `JoinRoom` (:68) `room.Participants.Count > 0 && room.Pin != null` — once the room empties (or after restart), the next joiner bypasses the PIN and becomes host (could clear it). If intended, document; otherwise enforce whenever `Pin != null`.
- `SetRoomPin` (:640) allows anyone when `HostConnectionId` is empty (related).
- Server-side PIN has no format validation (lobby UI promises "4–8 digits"); cap length/charset server-side.
- `JiraService.FetchIssuesAsync` has a hard 50-issue cap, no pagination; Atlassian is deprecating `/rest/api/3/search` in favor of `/rest/api/3/search/jql` — plan a migration.
- Chat history is not stored — late joiners see nothing (likely by design; document).
- No permission checks on RevealVotes/ResetVotes/HideVotes/SetCurrentStory/CompleteStory/DeleteStory/StartTimer — any participant (even observers/ghosts) can fire them; the settings lock only covers 4 settings. Decide whether destructive ones (DeleteStory, ResetVotes) should honor `SettingsLockMode`.
- `AvatarMove` clamps x/z but not `yaw`.

## C. Client bugs

### 🔴 C1. Sound settings key chaos — several sound features are no-ops
Four different "mute all" keys exist; only one is real:
- Canonical: `es_allSoundsOff` ('1'/'0') — wwwroot/js/audio.js:4–20 (`getAllSoundsOff`/`saveAllSoundsOff`).
- wwwroot/js/site.js:387/393 `_applySoundChoice('none'/'broadcast')` writes **`audio-all-off`** (that's the checkbox DOM id, not a storage key) → the N5 sound-preference prompt's "🔇 No sounds" choice mutes nothing.
- wwwroot/js/room.js:1725 `_promptSoundPreferenceOnce` reads **`audio-all-off`** → already-muted users still get prompted.
- wwwroot/js/site.js:1082 `_synthPlayCheck` reads **`es_soundAllOff`** → card-animation synth sounds ignore the global mute.
- wwwroot/js/site.js:310 `tabResetDefaults('tab-audio')` removes **`es_audioAllOff`** (a fourth variant) plus `es_timerAudio`/`es_ambientAudio`/`es_soundReceive`/`es_voiceSettings` — audit these against the keys the audio/voice modules actually use.

Similarly: site.js:390/392 `_applySoundChoice('local'/'broadcast')` writes `es_soundReceive` with `{receiveEnabled, showSubtitle}`, but room.js:2514 reads `es_soundReceiveSettings` with `{receive, subtitle}` → the "🎵 My sounds only" and "📻 Received only" prompt choices do nothing.

Fix: route everything through `getAllSoundsOff()`/`saveAllSoundsOff()` and room.js's `_getSoundReceiveSettings` key/shape; grep for all variants (`audio-all-off`, `es_soundAllOff`, `es_audioAllOff`, `es_soundReceive`) and unify.

### 🔴 C2. `_RS3D_VERSION` cache-bust not bumped for the pending room-scene-3d.js changes
Views/Room/Index.cshtml:472 still says `'p7-1'` while wwwroot/js/room-scene-3d.js carries ~224 lines of uncommitted Feature8 changes. The 3D module is loaded via dynamic `import('/js/room-scene-3d.js?v=' + _RS3D_VERSION)`, so cached clients keep the old module. Bump the constant with every rs3d change (and remember the project rule: restart dotnet after wwwroot JS edits).

### 🟡 C3. Lobby PIN saved under the raw room name, read under the canonical one
Views/Home/Index.cshtml:100 stores `sessionStorage['es_roomPin_' + room]` with the name as typed; room.js:154 reads `es_roomPin_ + ROOM_CONFIG.roomName` (normalized: lowercased, stripped). Typing "MyRoom" + PIN at the lobby loses the PIN and re-prompts. Fix: normalize in Home/Index before storing (lowercase + strip to `[a-z0-9-_]`, mirroring `RoomService.NormalizeName`), and use the same normalization for the recent-rooms PIN badge check (:121).

### 🟡 C4. Private reactions lose the sender
room.js:672 calls `_reactionFloatFromBadge(null, emoji, senderName)` but the function (room.js:2301) is `(senderCid, emoji)` — the name is ignored, so AD6 private reactions float anonymously mid-screen. Fix: accept an optional third param and show "from {name}" (small label under the emoji), or reuse `_showToastAD`.

### 🟡 C5. Stale selected card after reconnect/RoomState
The `RoomState` handler (room.js:168) replaces participants (my `hasVoted` may be false after a reconnect) but never syncs the local `selectedVote`/card highlight, so the UI shows a selected card the server doesn't have. Fix: in the RoomState handler, set `selectedVote = null` (or re-invoke `CastVote(selectedVote)`) when my participant entry has `hasVoted === false`, then `renderCards()`.

### 🔵 C6. Minor client items
- room.js:1546 `exportCSV` doesn't quote `finalEstimate` — a custom estimate containing a comma breaks the CSV.
- room.js:1666 bare `R` resets votes; after a reveal there's no confirm — a stray keypress wipes the round for everyone. Consider confirm-always or removing the single-key binding.
- Views/Home/Index.cshtml:120–126 `loadRecentRooms` injects the raw stored room name into `innerHTML` (self-XSS only, via localStorage) — escape it.
- shame.js is loaded twice on the room page (_Layout.cshtml script block AND Views/Room/Index.cshtml:450) — harmless today (var/function decls only) but remove the duplicate.
- room-scene.js `syncParticipants` and RS3D cap the scene at 16 participants silently — show a "+N more" indicator or document.
- In 2D top view, ←/→ keys steer the avatar (capture-phase, stopImmediatePropagation — room-scene-3d.js:2082), so the vote-card arrow navigation (room.js:1692) stops working whenever the 2D scene is mounted. Intentional Kumospace-style, but document it; `,`/`.` still navigate cards.
- wgt-test.js (a console test harness) ships in production wwwroot — exclude from publish or move to a dev folder.
- `settingsResetAll` (site.js:336) wipes Jira credentials and recent rooms (keepKeys only preserves player name/emoji/avatar/soundAsked) — confirm intended.
- `_handleRemovedFromRoom` (room.js:3113) uses blocking `alert()`.

## D. Security notes (accepted-risk callouts, verify intent)
- Jira email + API token are stored in plaintext localStorage (site.js:1696) and sent through the hub on every import/write. Same trust model as the rest of the app, but worth a note in README/About.
- `Program.cs:40` clears `KnownIPNetworks`/`KnownProxies` so `X-Forwarded-*` is trusted from any source — required for IONOS, but means clients can spoof scheme/IP; nothing security-critical consumes them today.
- `TriggerCustomSound` relays up to 700 KB base64 audio to the whole group (rate-limited 3 s) — bandwidth amplification with many participants; consider lowering the cap.
- Good: Jira SSRF domain validation, media magic-byte checks + quotas, atomic room-file writes, server-side rate limiting, restart-stale-participant clearing.

## E. Performance
- No significant hot-path issues found. Coalesced 2-second room persistence is sound. `_rebuildSeating` full rebuild per event and per-event `renderParticipants` are fine at ≤16 participants.
- B2/B3 (locking) are the only correctness-adjacent perf items.
- `_walkCollidesAt` (new Feature8 code) does O(furniture+props) circle tests per tick — fine at this scale.
