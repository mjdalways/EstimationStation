EstimationStation — Feature Plan v4.0

Continuation of v3.0. All v3.0 groups A–O are complete. This plan covers the next wave: reveal drama, sprint intelligence, game mechanics, Jira write-back, mobile, and persistence.

📅 Created 2026-05-16 ✅ v3.0 + 8 v4.0 groups shipped 📋 10 groups pending 🔧 Stack: ASP.NET Core 10 / C# / SignalR / Bootstrap 5 / Vanilla JS
Sprint context Typical sprint: ~10 stories, 5–8 need pointing (bugs, spikes, and tech-design stories are pulled from Jira but not pointed). Slot machine reveal and suspense ordering will be most impactful at these small counts. Historical trend data should accumulate meaningfully within a single PI or quarter.

Remaining v4.0 Features

Group E — 🎵 Timer Audio Customization plan-E-timer-audio.md

Easyaudio.js · _Layout.cshtml
  • Built-in themes: Jeopardy (think music, final 10s), Jaws (bass pulse, final 15s), Ticking Clock (simple), Silent (current behaviour).
  • Custom upload: same base64 pipeline as the existing custom soundboard. Max 10s / ~800KB. Loops during countdown, stops on timer end or cancel.
  • Trigger point: configurable — plays from start, or only in the final N seconds (e.g. last 10s). Default: last 10s.
  • Setting: es_timerAudio = { theme: 'jeopardy' | 'jaws' | 'ticking' | 'silent' | 'custom', triggerAt: 10, customBase64: null }.
  • In Settings → Events, add a "Discussion Timer Sound" section with radio buttons + trigger-point slider + custom upload slot + test button.
  • Audio synthesised via AudioContext for built-in themes (no audio files to ship); custom upload uses existing Audio(base64) pattern.

Group C — 📊 Sprint Dashboard plan-C-sprint-dashboard.md

Mediumroom.js · site.css · _Layout.cshtml
  • Running points total: below the story list, a small chip: 🎯 34 pts committed. Sums finalEstimate for completed stories where the value is numeric. Non-numeric (?, ☕, XL) are excluded silently.
  • Current session sparkline: SVG polyline in the vote history panel showing estimate values across stories in order (e.g. 3→5→8→5→13). Renders after 2+ completed stories. Width fills the panel; height 40px.
  • Historical data: on session end (or story completion), append { date, roomName, stories: [{title, estimate}] } to es_estimationHistory in localStorage. Cap at 20 sessions.
  • Historical sparkline: in Settings → About (or a new Analytics tab), show a larger trend chart across all stored sessions. Average estimate per session plotted over time. Toggle between current-session and all-time view.
  • Sprint context note: at 5–8 pointing stories per sprint this trend will be meaningful within 3–4 sprints.
  • No backend changes — all localStorage. If the room is shared, each participant builds their own history independently.

Group F — 🔒 Room PIN plan-F-room-pin.md

MediumViews/Home/Index.cshtml · room.js
Backend done JoinRoom hub method already accepts an optional pin parameter and validates it server-side. Only the home-screen UI (input field + PIN prompt dialog on mismatch) remains.
  • Creation: on the home/join screen, an optional "Set PIN (4 digits)" input. If provided, stored on the Room model as string? Pin.
  • Join enforcement: JoinRoom hub method gains an optional string? pin parameter. If the room has a PIN and the supplied value doesn't match, the hub sends Error("Incorrect PIN") and does not add the participant.
  • Client: if the user attempts to join a PIN-protected room and gets an error, a PIN prompt dialog appears. The room URL does not expose the PIN — it stays out-of-band (shared verbally or in the meeting invite).
  • No PIN = no change to existing join flow. Rooms created without a PIN remain open as today.
  • Security note: PIN is a deterrent against accidental joins, not cryptographic security. It is stored in memory only (not hashed) and transmitted over WSS.
  • The room creator can see a small 🔒 badge in the room header indicating PIN protection is active.

Group J — 📱 Mobile Experience plan-J-mobile.md

Medium-Hardsite.css · room.js · _Layout.cshtml
Design principle Desktop is primary. Mobile should be usable and functional, not a feature showcase. On small screens: dial back animations, collapse panels aggressively, ensure vote cards are thumb-reachable.
  • Layout: stories panel slides in as a bottom sheet on mobile (swipe up, tap overlay to dismiss). Main content fills the viewport. Navbar collapses to just the title + ⚙️ button.
  • Vote cards: minimum 52px tap target. Wrap into 4-per-row grid on narrow screens. Selected card gets a bold border (not just colour, which may not be visible in sun).
  • Animations: prefers-reduced-motion already respected; additionally gate confetti, fireworks, battle arena, and slot machine behind window.innerWidth > 600 or a "Lite mode" flag set automatically on mobile. User can override in settings.
  • Inputs: chat input, story add input, and JQL input all get inputmode attributes to trigger the right mobile keyboard.
  • Testing: Chrome DevTools device emulation for iPhone SE (375px) and Pixel 7 (412px) as target breakpoints.
Mobile bugs fixed in Group L
  • Vote button — now flashes a blue outline pulse on the card grid after scrolling.
  • Chat button — shows "No one else here yet" toast when alone; does not open empty panel.
  • Stories sidebar — close button uses correct bottom-sheet animation; no longer styled blue; backdrop shown on open.

Group K — 💾 Room Persistence investigation-room-persistence.md

HardProgram.cs · RoomService.cs · new IRoomRepository.cs · new SqliteRoomRepository.cs
Investigation status Requires architectural decision on storage backend before implementation. See questions below.
  • Problem: RoomService is a singleton in-memory dictionary. A server restart (common on IONOS shared hosting) drops all rooms mid-sprint.
  • Option 1 — SQLite: Add Microsoft.Data.Sqlite. IRoomRepository with SqliteRoomRepository. Snapshot room state on every mutation (story add/complete, vote reveal). Simple schema: rooms(name, json_blob, last_activity). On startup, hydrate from DB. TTL: auto-delete rooms inactive for 7 days.
  • Option 2 — JSON file per room: write rooms/{name}.json on mutation. Simpler, no dependency. Works on shared hosting without a DB engine. Less atomic, but room data is low-contention.
  • Option 3 — Periodic snapshot only: background timer every 60s writes dirty rooms to file. Lose up to 60s of state on crash. Easiest to implement.
  • Recommendation: Option 2 (JSON file per room, write-on-change) for IONOS compatibility. Wrap behind IRoomRepository so SQLite can be swapped in later. File path configurable via appsettings.json.
  • In-scope: room state (stories, participants, votes). Out-of-scope: vote history, analytics (those are client localStorage).
  • Concurrency: existing lock(room) pattern extends naturally — lock before write, SemaphoreSlim per room for async file I/O.

N3 — Move "Reveal Majority First" to Room-Level Global Setting

This toggle is currently localStorage-only but affects reveal ordering for all participants — it should be a room-wide broadcast setting, not a personal preference.

  • Add ToggleRevealOrdering(bool enabled) hub method in PokerHub.cs; store on Room model; broadcast RevealOrderingChanged(bool) to room
  • Move the checkbox to the in-room settings panel (near auto-reveal), not the settings modal

N4 — Collapsible Sections Within Settings Tabs

The Events/Celebrations tab is very long and hard to scan. Group controls into labelled collapsible sections.

  • Celebrations tab groups: Confetti, Fireworks, Balloons, Lava Lamp, Card Reveal, Shame & Counter-Spell, Miscellaneous
  • Audio tab groups: Broadcast, Local, Timer
  • Use Bootstrap collapse divs with a <button> header; default: first group open, rest closed
  • Remember last-open state per tab in localStorage (es_settingsOpen_*)

N5 — Sound Confirmation on Room Join

If any sounds are configured and a user joins a room, they should be asked once per session what sound mode they want — avoiding surprise audio in meetings.

  • Trigger: after connection.start() succeeds AND any sound setting is enabled AND sessionStorage.getItem('es_soundAsked') is not set
  • Show toast/modal: "🔊 Sounds are configured. Choose your preference:" — [All sounds] [Local only] [Broadcast only] [No sounds]
  • Selection updates Audio settings; set sessionStorage.setItem('es_soundAsked','1') so it only shows once per page load

Won't Do / Permanently Deferred

FeatureReason
🔮 Oracle Prediction (v3.0 Group L, v4.0 Group F candidate) Fun concept but adds a pre-reveal waiting phase that disrupts the flow for quick sessions. The 10s window feels like friction when the team just wants to see the votes. Removed twice — shelved.
😈 Devil's Advocate (v3.0 Group N, v4.0 Group G candidate) Interesting narrative mechanic but requires server-side secret state per participant, complicates the shame/outlier logic, and can feel unfair to new players who don't know the role exists. Removed twice — shelved.
📋 Copy estimates to clipboard Superseded by Jira write-back (Group H). Teams using Jira get estimates synced automatically; teams not using Jira can manually note estimates in the existing vote history view.
🔵 Azure DevOps / Linear import Same proxy pattern as Jira M1 so technically straightforward, but target user base is Jira-first. Revisit only if there is clear demand from actual users.
🌡️ Re-vote nudge banner Teams already have the hot/cold meter and stats bar showing min/max/average — sufficient signal to self-organise a re-vote discussion. An additional banner would be noise.
🐉 Boss Fight Arena (v3.0 Group K) High complexity state machine, procedural boss art, HP tracking. Fun concept but scope dwarfs value for a planning tool. Revisit only if the app pivots to pure game.
🔄 Auto-reveal as personal preference Confirmed: ToggleAutoReveal has no host check — any participant can toggle it and the checkbox renders for everyone. A personal override would create divergent room state (some participants see manual reveal, others see auto). Won't Do.
⚙️ Move hardcoded JS limits/timings to appsettings.json Server config is for server concerns (DB paths, auth keys, CORS). Client animation timings and thresholds belong in JS/localStorage where users can tune them directly via the settings UI. Won't Do.
📐 Range Voting (min/max instead of single point) Breaking API change to CastVote and all downstream handlers. Disrupts every other feature. Consensus on a range is also harder to act on.
🗂️ Jira Integration — on-premise / Data Center Different auth (OAuth 2.0, Kerberos). Scope creep. Jira Cloud covers the target user base.
